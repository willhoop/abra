## 2. THE DEFECT: A RAMPAGE THAT REACHED NOBODY ARMED THE LOCK ANYWAY

`outrage` is `self: { volatileStatus: 'lockedmove' }` (`data/moves.ts:13085`; `uproar` carries the
same field with `'uproar'`). `self` is applied by `Battle.actions.selfDrops`
(`sim/battle-actions.ts:1317-1335`), which is called from `spreadMoveHit` at `:1096` — the
Champions override keeps that line verbatim at `data/mods/champions/scripts.ts:385`.
`spreadMoveHit` is **step 7** of `trySpreadMoveHit`'s `moveSteps`, and that loop breaks at
`if (!targets.length) break` (`:606-609`) the moment every target has been filtered false. A Fairy
body answering an Outrage at step 2 (`hitStepTypeImmunity`) therefore leaves the user **free** —
and so does a total miss or a shield. `selfDrops` then opens `if (target === false) continue`
anyway.

This engine armed `_mtLock` with no gate at all. The recharge rider one block up
(`rechargeArmedAtSelfDrops`) has carried `_reached > 0` since WIRE 43; the lock never got the
same gate.

**The fix is one added branch**, `engine/medicham2-browser.js`:

```js
else if(!(m._mtLock&&m._mtLock.move===a.move.id)&&!(_reached>0)){
  MEDSEEN.lockSkippedNoTarget++;
}
```

**Only the arming is gated, deliberately.** The enclosing block also runs Uproar's wake sweep —
`uproar.onTryHit` is step 1, *above* the type immunity, so it cures sleepers even on a board the
move cannot reach — and the `expiresAtMove` fatigue, which hangs off `AfterMove` and runs whatever
the move returned. Gating the whole block would silently take both.

**The position is untouched and that is a separate open defect.** The authority arms this inside
the hit loop; this site is below the step list. It matters for Uproar alone (`lockedmove`
announces nothing; `uproar.onStart` writes `|-start|<user>|Uproar`). Named, not fixed.
