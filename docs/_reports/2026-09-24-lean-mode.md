# Lean mode for search playouts: the same boards, less work per turn

**Date:** 2026-09-24. **Division:** ENGINE. **Line:** abra/regmc 0.111.3 on the branch, landed in main as 0.116.1 (PATCH).
**Base:** main `76905129` plus the cherry-picked normaliser memo (`b93c9797`, here `fc4cffac`, renumbered 0.111.2).
**Branch:** `worktree-agent-a48f2802cb3153322`. Not merged, not pushed.

## Verdict

- **Speed, lean against full, same process, same turns, main-thread CPU, paired blocks:**
  - per turn: **1.18x to 1.35x** turns per CPU-second (block medians, three runs; whole-run 1.22x to 1.33x; §4);
  - MILTANK playouts: **1.25x to 1.33x** playouts per CPU-second (block medians, four runs), with the cell values
    hashed equal (§4).
- **Lean is board-identical to full** on every game of the Reg M-C `--games 1200` lattice and on 300 human-sheet games
  (§3). The test is `solver/tests/test-lean-mode.js`. It was shown RED on a deliberate break first: `MEDI_LEAN_BREAK=1`
  makes a lean turn skip Leftovers' heal, and both populations report disagreements.
- **Non-lean is byte-identical to base** per game on the pinned Reg M-C `--games 1200` differential (§2).
- **MILTANK uses lean** (`solver/miltank/rollout.js`, cherry-picked from `playout-speed`): each playout's own copy is
  made lean. `MILTANK_LEAN=0` turns it off for an A/B.
- **Nothing that decides order was touched**, as Will required: the Update speed re-sort, every `effSpeed` that feeds
  a sort, `volSeqSync` and the residual handler sort run in lean exactly as in a full battle.

## 1. What lean mode turns off

A battle built with `newBattle(a, b, {lean: true, rng})` (or made lean with `API.makeLean(S)`) carries `S._lean`.
Every turn it plays runs inside the engine's `leanRun`, which for that turn only does the following.

| Work | Lean | Why it is safe |
|---|---|---|
| Tag lookups (`TAGS.param/has/tagsFor`, ~1,830 a turn measured) | Answered by `engine/tags.js` `leanView()`: per kind, a table from the raw id to the record and a PRE-BUILT answer object (tag -> value). No `ASKED`/`COUNT` counting. | The same answers: the same record, the same `params[tag]` object, a fresh `{}` per call where the counting API makes one. The tables are rebuilt when the artifact object changes (`__setDB`) and at every lean battle. Micro-benchmark on the recorded call trace of a real workload: ~115 ns a call counted, ~45 ns lean. |
| `MEDSEEN` / `MEDFAILS` | Rebound to a private sink for the turn. | Counters only. Every gate, probe and census reads the real objects, which a lean turn never touches. |
| Protocol trace | Refused. A lean battle with a trace sink throws (`newBattle`, `clone`, `battleTurn`). `TR` is null. | The trace was already off by default. This makes lean an explicit no-trace mode. |
| Event-address log (`MID_LOG`) | Not written. The repeat map (`MID_NTH`) that feeds the dice is kept. | The log has no reader in the engine. The differential reads it only in the middle arm, which is never lean. |
| `sdEachEventOrder` live speed | Not computed when the body has a cached stamp (`_sdSpe`). | With a stamp, the sort key is the stamp, and `live` feeds only `MEDSEEN.updateSortCachedDiffersLive`. With no stamp the live speed IS the key and is computed as before. Audit of `effSpeed` and every callee (`statWithBoost`, `ubMult`, `ubLegacyMult`, `sdChain`, `sdModify`, `suppressesWeather`, `weatherId`, `terrainId`): they write locals and counters only, so skipping the call removes no state write. Magician's copy of the same read is skipped the same way. |
| Eject Button same-speed tie witness | Skipped. | It computes speeds only to bump `MEDFAILS.ejectSwitchOrderTie`. The sort above it is unchanged. |
| Emergency Exit "other door" witness at the top of the turn | Skipped. | It reads a tag and writes `_eeHP` for `MEDFAILS.emergencyExitOtherDoorUnmodelled`. `_eeHP` has no other reader (grep: one read, in that counter). This is the one field lean holds differently, and the test names it. |
| An attack action's price (`playerActionPrimary` `d`, `acc`) | `null`. | A valuation for callers that price a click. No step of a turn reads it outside the `MEDI_ORB_STALE_RANGE` restore arm, where lean computes it as before. `null` makes any reader throw, so "never read" is loud. It was ~6% of a turn (`dmgRange` + `hitProb` per action built). |

**For every battle, lean or not: the entry is a thin door.** The scope and lean tests used to be the first lines of the
~22,000-line turn body, so every API battle entered the body twice a turn, once only to delegate. They now sit in a small
`battleTurn` in the same order, and the body is `battleTurnBody`. This is a refactor and plays the same bytes (§2).

**Not touched, by instruction:** the Update speed re-sort, `volSeqSync`, the residual handler sort, `residualOrder`'s
speed reads, and every other speed read that feeds an order.

## 3. Lean is board-identical to full

`solver/tests/test-lean-mode.js --release 1886fadf0679 --games 1200 --human 300`.

- **Lattice.** The differential plays every game of the Reg M-C `--games 1200` lattice as the gate plays it, with
  `tests/medicham_api_diffhook.js MEDI_API_HOOK=lean` preloaded. At each battle's first turn it takes a FULL copy and a
  LEAN copy. Both play the whole game beside the real one, on the real turns' choices and a replay of the real turns'
  dice, and are never re-synchronised while they agree (they are re-taken only before a turn where the differential
  edited the real battle; see the corrections below). After every turn the whole battle graph is compared
  (`API.digestString`, less `_lean` and `_eeHP`), and the two copies must take the same draws, stream by stream. Every
  routed turn must be compared or named (a real turn that threw has nothing to compare). The hooked run's per-game
  fingerprint must equal the plain run's, so the checked games are the lattice's own games.
- **Human sheets.** 300 games from the human dataset's open sheets (`solver/arena/teams.js`, the humans' own bring).
  Each is played twice from scratch, full and then lean, on the same seeds. A seeded uniform policy over the rollout
  support is drawn from the full battle and replayed on the lean one. Every turn is compared, and so are the draw
  counts per dice stream and the winner.

| Population | Result |
|---|---|
| lattice: the hooked run is the lattice | per-game sample fingerprint byte-identical to the plain patch run over **955 games** |
| lattice: lean against full | **22,283 turns compared, 0 differ** (board and draws per stream), in 2,110 battle copies; every routed turn compared: none untranslated, no real turn threw. The pair was re-taken before 39 turns, where the differential had edited its real battle since the last turn (its planted-divergence proofs) |
| lattice: full copy against the real battle | equal after all 22,283 turns (less the trace-only fields `_trace`, `_chipFrom`, `_traceFainted`), so the two copies were playing the real game |
| human sheets | **300 games, 2,518 turns, 0 differ** (board and per-stream draw counts); the same winner in 300 of 300 |

**Shown RED.** `MEDI_LEAN_BREAK=1` makes a lean turn skip Leftovers' residual heal (one real board handler; it stamps
the real `MEDFAILS.leanBreakRestored`). Lattice (`--games 45`): 102 lean turns differ. Human sheets: 383 lean turns
differ. The break was first shown red on a 45-game lattice and a 24-game human slice while the test was being built.

**Two corrections to the instrument, made during the work, both in the harness and neither in the engine.**

1. The first full lattice run compared the lean copy's draws with the REAL turn's recording and flagged 2 turns (one
   game, turns 6 and 7) where the boards agreed and the dice did not. A diagnostic re-run with per-stream counts showed
   the lean copy and the full copy took exactly the same draws (acc 3, dmg 3, crit 3, sec 1, tgt 1 each) while the real
   turn took one more accuracy draw: the full copy had parted from the real battle too. The claim is lean against FULL,
   so the check now compares the two copies' draws stream by stream.
2. The next run counted 21 turns it could not compare: translating the actions onto the copies threw ("Cannot read
   properties of undefined (reading 'confusion')", 'aquaring', 'torment', ...). Those are turns right after the
   differential's planted-divergence proofs wrote volatiles, HP, status or items straight into the real battle
   (`engine/game_differential.js` `STATE_PLANTS`), so the copies no longer had the real battle's shape. The pair is now
   re-taken before any turn where the real battle's board moved since the last turn ended (39 turns), every routed turn
   is compared or named, and the test fails on any turn left uncompared. With that, the full copy also equals the real
   battle after every turn, which it did not before (17 turns).

## 4. Speed

Both arms run in ONE process on the same fixed workload. Blocks alternate the arm order, and main-thread CPU
(`process.threadCpuUsage`) is summed per arm. The per-block ratio cancels machine load. Absolute ms per turn moved 1 to
8 ms between runs on this machine (it was saturated all day), so only the ratios are reported as findings.

**Per turn.** `bench2.js` (scratchpad): 40 Reg M-C human-sheet games (8 pairs x 5 seeds), choices recorded once and
replayed by both arms, 16 blocks.

| Run | full ms/turn | lean ms/turn | whole-run ratio | block median (q25-q75) |
|---|---|---|---|---|
| 1 | 8.01 | 6.33 | 1.27 | 1.35 (1.22-1.36) |
| 2 | 6.23 | 4.69 | 1.33 | 1.18 (1.17-1.32) |
| 3 | 1.16 | 0.95 | 1.22 | 1.26 (1.22-1.30) |

4,848 turns per arm per run, the same turns in both arms. The absolute column moved 7x between runs; the ratio did not.

**MILTANK playouts.** `pobench.js` (scratchpad): `solver/bench/playout_bench.js` positions and jobs (27 positions,
k = 6, depth 1). One sampled world per job per block, one playout per cell, CRN seeds. A full rollout and a lean
rollout run in one process.

| Run | full playouts/CPU-s | lean playouts/CPU-s | whole-run ratio | block median (q25-q75) | cell values (both arms) |
|---|---|---|---|---|---|
| 0 | 165.8 | 208.3 | 1.26 | 1.28 (1.18-1.32) | `e610a6ce35f2f603` |
| 1 | 135.6 | 158.0 | 1.17 | 1.25 (1.10-1.31) | `e610a6ce35f2f603` |
| 2 | 463.8 | 592.5 | 1.28 | 1.27 (1.23-1.31) | `e610a6ce35f2f603` |
| 3 | 74.3 | 104.8 | 1.41 | 1.33 (1.24-1.33) | `e610a6ce35f2f603` |

7,776 playouts per arm per run (8 blocks). A playout also pays for its copy (`v8.deserialize`) and the random joints'
menu reads, so it gains less than a bare turn.

`solver/bench/playout_bench.js` alone (`values_sha 951ecf8d01c9ff85`, `decide_sha ed053d3c43cc77b7`) prints the same
two hashes with `MILTANK_LEAN=0` and with lean on.

Where the rest of a lean turn goes (`--cpu-prof`, lean): the turn body itself, the move pipeline, damage, `volSeqSync`
and the residual shadow (off limits), `effSpeed` for the sorts (off limits), and GC. The tag layer: a real workload's
recorded call trace (1,827 tag calls a turn; the top askers are `weatherSuppression` 186, `speedMult` 160 and
`speedCond` 160 a turn, all from speed reads) replayed through each accessor cost ~115 ns a call counted and ~45 ns
lean (`tagmicro.js`, three repeats).

## 5. MILTANK

`solver/miltank/rollout.js` (from branch `playout-speed`, commits `562dc055`, `ab8e010d`, `d441b52a`, `eaf93368`,
cherry-picked here as solver-only commits): `playout` makes its own copy lean (`API.makeLean`) and runs the whole playout
(turns, random joints' menu reads, leaf) inside `API.leanRun`. The world and the prepared buffer are not made lean, so
their digests are unchanged. `COUNTERS.leanPlayouts` says which ran. `opts.lean === false` or `MILTANK_LEAN=0` plays
full.

## 7. What was not done, and why

- `node engine/status.js --write` was not run. In a worktree it writes the missing untracked frozen pools as fact
  (memory: status-write-corrupts-from-a-worktree). The coordinator stamps the ledgers on main.
- The census was not regenerated. No mechanic moved, and non-lean plays the same bytes.
- Releases cut here (Reg M-C `1886fadf0679` patch, `318ccd937118` base, `f6cdc996f877` a development cut; Reg M-B
  `4f4dd1005ade` patch) and `d9d69d58ef31` (copied from the main checkout) sit uncommitted in the worktree's
  `data/releases/`. `data/engine-release.json` was restored, and `data/engine-release-regmc.json` (created by these
  cuts) was removed.
- Not attempted: a per-battle cache of speeds, or any change to `volSeqSync` or the residual sort (Will's constraint).
