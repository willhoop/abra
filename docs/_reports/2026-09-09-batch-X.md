Batch U wrote *"THE OHKO CARD IS UNDIAGNOSED AND IS SAID SO. The authority's only `-immune … [ohko]`
site needs `dynamax`, a level gap, or an Ice-typed target; the card is L50 Sheer Cold into a L50
[non-Ice body]."* **The third clause is the live one and the target had become Ice-typed** — but the
mechanism does not depend on settling that, because the engine's own reader already knew:


`continue` is the load-bearing word: the authority leaves the per-target loop **above its own
`randomChance`**. This engine expressed the immunity as `hitChance -> 0`, and **zero is finite**, so
`accMustRoll` said yes, `_stepAccuracy` spent an `acc` draw, the draw came back above zero, and the row
left through the MISS door with the miss's line on it. `MEDSEEN.ohkoImmune` had been counting this exact
case since the OHKO tag was wired.

**SO IT IS TWO DEFECTS IN ONE RETURN VALUE**, and the second is not narration: this engine consumed an
`acc` address the authority never consumed. The identity check tolerated it only because its floor is
0.9. `accDrawsTaken` is now asserted in both directions on every arm.

**The fix.** A shared predicate `ohkoTypeImmune(def, id)` next to `accMustRoll`, called by BOTH
`hitChance` (which keeps returning 0, so nothing that PRICES a click moves) and `_stepAccuracy` (which
announces and returns without drawing). The two other clauses of the same `else` are FORMAT FACTS and
are stated rather than modelled: Champions is Level 50 throughout and Dynamax does not exist here.
The authority's `!target.isSemiInvulnerable()` guard is not restated either — `_stepInvuln` is the
FIRST step in the list and marks such a row `out`, and the driver skips an `out` row for every step
without `runsWhenOut`.

## 3. THE QUESTION THE BRIEF MOST WANTED ANSWERED: **CAN THE SUBSTITUTE FAMILY'S STEP LIST BE RESTRUCTURED?**

**Short answer: a correct slot cannot be created in the step list, and the reason is not the step list.
It is that this engine's MULTI-HIT LOOP is nested INSIDE `_stepApply` where the authority's is OUTSIDE
`spreadMoveHit` entirely. Fixing the doll properly is a LOOP-NESTING change, and batch N has already
built the machinery for it.**

### The authority, read whole

`hitStepMoveHitLoop` (`data/mods/champions/scripts.ts:459-532`) is the ARRIVAL loop, and `spreadMoveHit`
— all seven of its numbered steps, including step 0's `tryPrimaryHitEvent` where the doll is absorbed —
is its BODY. So for a two-arrival volley the authority runs step 0, step 1, step 2 … then step 0, step
1, step 2 … again. Every arrival gets its own doll check, its own effectiveness lines and its own damage.

### This engine

`_STEPS` is walked ONCE per move (`_walk`, step-outer/row-inner), and the arrivals are a loop **inside
`_stepApply`** — `for (let i = R.pkFrom; i < _packets.length; i++)`, which is where `R.crits[i]`,
`R.reprice(crit, i)`, the per-arrival effectiveness/crit emission (line ~37732) and batch V's
per-arrival doll clamp all live. `_stepDamage` emits the effectiveness line only for the
**single-packet** case (line ~36610, `if (TR && !_multiPk)`); for a volley that line is emitted inside
`_stepApply`'s arrival loop.

### So what would a "step 0" doll step cost

A new step above `_stepDamage` would have to, for each row whose target holds a doll: price the damage,
emit that row's own effectiveness line, absorb into the doll, and mark the row `out`. That is
constructible, and the DICE probably do not move — `_subAddr` already pins the doll's crit and damage
rolls to `_accLastSlot`, `nth` counts per address STRING, and the doll is already visited before any
live body in row order, so the `nth` assignment is unchanged. **That would have to be measured and not
assumed.**

**But it only works for arrival 1.** Arrivals 2..n never leave `_stepApply`, so their doll absorb has to
stay where batch V put it. The doll logic would then exist in TWO places — which is exactly the
duplication batch V's fix removed, and it is the shape CLAUDE.md's FACTS-ARE-GLOBAL rule forbids. A
volley that breaks a doll on arrival 1 and lands on the body for arrivals 2 and 3 would be resolved by
two different implementations of the same rule.

### The change that IS correct, and it already has a precedent in this file

**Make the ARRIVAL loop the outer loop over the `_stepDamage` … `_stepAfterHitField` segment**, which
is exactly `spreadMoveHit`. Then a step-0 doll step is correct for every arrival, and the per-arrival
machinery inside `_stepApply` collapses into the segment.

Batch N (2026-09-07) has already built this for `smartTarget`: `_smartRowMajor` looks up
`_STEPS.indexOf(_stepDamage)` and `_STEPS.indexOf(_stepAfterHitField)` **dynamically** — a hard-coded
pair "would silently cut the list in the wrong place the first time a step is inserted" — and re-walks
that segment per body. The same indices, iterated per ARRIVAL instead of per body, are the volley
version. Batch N's header even names the boundary correctly: everything above `_stepDamage` is
`trySpreadMoveHit`'s pre-loop steps and everything below `_stepAfterHitField` is below the loop in the
authority too.

### What it would cost, said plainly

- **It is the whole batch.** Every per-arrival mechanism now inside `_stepApply` — `R.pkFrom`,
  `R.pkIdx`, `R.crits`, `R.reprice`, `_dollPaid`, `_absorbed`, `_hpBeforePackets`, `R._berry`,
  the Focus Sash and Endure clamps, `_stepBuffOnHit(R, 1)`'s interior call, `_landed`/`R.hitLanded` —
  moves from "a loop I control" to "state carried across seven step invocations". Each is a place the
  arrival index is currently implicit and would have to become explicit.
- **`_stepUpdate` is the declared trap.** Batch N deliberately left it step-major, because this engine
  raises one `eachEvent('Update')` per MOVE where the authority raises one per HIT, and moving it inside
  the segment "would trade a declared and measured gap for an undeclared one". Under an arrival-major
  walk that gap CLOSES rather than moves — which is a second behaviour change riding in on the first,
  and it has its own probe (`probe_multihit_update.js`) that would have to be re-aimed.
- **BOARD-MATERIAL must be checked after every single move**, and it is currently 0 of 958. This is the
  one change in the queue that can plausibly break it.
- **`test-resolution-order.js` carries a DECLARED `KNOWN-OPEN` arm for exactly this** — "the authority
  wraps the whole step list once per hit and this engine wraps it once per move" — and closing it is the
  arm's own subject. It would go from declared-open to green, which is the receipt that the restructure
  landed.

**So: not cheaply, and not as a step insertion. It is a one-batch loop-nesting job with a precedent, a
dynamic segment lookup already written, a declared open arm waiting to close, and one named trap
(`_stepUpdate`). That is a plan rather than a deferral, and it is the honest answer to a question four
batches have left on the same diagnosis.**

### 4d. THE POST-KO SWITCH-IN ORDER — **THE SORT KEY IS THE FAINTED BODY, NOT THE ONE WALKING IN**

```
ordering :: |switch|p2a|archaludon,l50|H/H <> |switch|p1a|gholdengo,l50|H/H
```

Derived rather than assumed, because the brief warned about exactly this. A replacement is
`{choice: 'instaswitch', pokemon, target: targetPokemon}` where `pokemon = this.active[index]` — **the
FAINTED body** — and `target` is the one coming in (`sim/side.ts#chooseSwitch`). `Battle#getActionSpeed`
then writes `action.speed = action.pokemon.getActionSpeed()`, i.e. **the outgoing corpse's Speed**, and
`BattleQueue#sort` is `speedSort` over `comparePriority` (order ASC — all `instaswitch` at 3 — priority
DESC, speed DESC, ties to `prng.shuffle`).

**This engine sorts by the INCOMING body**: `entryOrder(all, entrants, field)` is handed
`{nx: <the arriving mon>, spe: effSpeed(<the arriving mon>, …)}`. That is a different key, and it is a
concrete lead. **It does not yet explain the card** — on both engines Pelipper (base 65) came in FIRST,
which neither key predicts from base stats alone, so the real teams' SP spreads are in play and the
next batch needs the actual stats before writing a probe. Also unresolved: whether the fainted body's
`getActionSpeed()` still sees its own ability (`findEventHandlers` requires `target.isActive`, and
`faintMessages` sets that false), which would matter for a Swift Swim body dying in rain — which is
exactly this card.

### 4f. THE STAMINA / SPICY SPRAY CARD — **NOT ATTEMPTED, AND THE ENGINE'S OWN DERIVATION IS WRONG IN ONE PLACE**

```
ordering :: |-boost|p1a|def|1 <> |-status|p2b|brn|[from]spicyspray
  showdown  |-boost|p1a: Archaludon|def|1   |-status|p2b: Milotic|brn|[from] ability: Spicy Spray
  medicham2 |-status|p2b: Milotic|brn       |-boost|p1a: Archaludon|def|1|[from] ability: stamina
```

A Muddy Water into an Archaludon (Stamina) and a Scovillain (Spicy Spray) — two bodies, one ability
each, both halves of one `runEvent('DamagingHit', damagedTargets, …)`.

**THE SORT IS NOT `speedSort` AND THE ENGINE'S `_stepBuffOnHit` HEADER SAYS IT IS.** Read whole:

```
if (['Invulnerability','TryHit','DamagingHit','EntryHazard'].includes(eventid)) {
  handlers.sort(Battle.compareLeftToRightOrder);            sim/battle.ts:789
}
compareLeftToRightOrder = order ASC (default last) → priority DESC → INDEX ASC   sim/battle.ts:421
findEventHandlers: handler.index = i, the position in damagedTargets              sim/battle.ts:1039
```

**Deterministic, index-major, no speed and no tie.** The `_stepDamagingHitLate` header (batch Q2) has
this right; the `_stepBuffOnHit` header (2026-09-08) says "`speedSort`ed together" and concludes that a
fix "reorders draws at a shared address and moves boards … needs its own batch with a bisect budget".
**The premise of that conclusion is wrong.** The reorder is deterministic, so the dice risk is confined
to the `nth` counting at `_reactAddr`'s single shared address, which is far narrower than a speed sort
would be.

**Why I still did not fix it.** The correct walk is two passes — every `onDamagingHitOrder: 1` handler in
row-index order, then every default-order one in row-index order — and **this engine cannot tell the two
apart from `data/tags.json`**: `punishesAttacker` carries no order field. Landing it means adding an
`order` param in `engine/tag_dex.js` and regenerating `data/tags.json` **and** `data/abra-tags.js`, both
of which are frozen SOURCES; that is a large blast radius for one narration cause and it is a batch of
its own.

**AND A SECOND ERROR IN THE SAME HEADER, DERIVED:** it states that `_stepDamagingHit` "is where every
`onDamagingHitOrder: 1` member lives (aftermath, electromorphosis, innardsout, ironbarbs, roughskin,
windpower)". Filtered over the format, six abilities carry `onDamagingHitOrder: 1` and **`electromorphosis`
is tagged `buffsHolderOnHit`**, so it is in `_stepBuffOnHit` — a step BELOW. One of the six is already on
the wrong side of the split the header describes.
