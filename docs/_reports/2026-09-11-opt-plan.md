# The MEDICHAM optimization pass: plan and profile (ENGINE, 2026-09-11, ROADMAP #130)

Planning and profiling only. No engine, test or ledger file was edited. Every file this pass wrote is
in `data/verification/opt-plan-2026-09-11/`, plus this report.

## Verdict

**A rollout turn's time goes to three places.**

1. **`battleTurn`'s own body: 18.1% self.** After warm-up it runs in V8's baseline tier (Sparkplug).
   V8 compiled it to Maglev repeatedly and threw the code away each time, with the reason `wrong map`.
2. **Tag lookup (`engine/tags.js`): 16.9% inclusive.** About half of that is the regex that
   normalises the id, which runs on every call (`norm`, 8.1%).
3. **Speed: `effSpeed` plus `residualOrder`, 13.0% inclusive.** Speed is recomputed for every body in
   every residual group and in every update pass, and each computation makes three or four tag
   lookups.

**Protocol text is not a rollout cost.** The trace is off in every rollout (`TR` is null), and arming
it adds 9.5% per turn. A "rollout-only mode that skips narration" would therefore save about
nothing, and it is not recommended.

**The top three candidates, all estimates and all unmeasured:**

| # | Change | Estimated gain |
|---|---|---|
| 1 | Memoise `norm` in `engine/tags.js`. It is pure, so the change is safe by construction. | 5–7% of rollout time |
| 2 | Stabilise the object shapes behind `battleTurn`'s `wrong map` deopts, so that it stays in an optimising tier. | 5–15%. The widest band here: the sites are not yet located, which is Batch 2. |
| 3 | Index tag membership in `engine/tags.js`, with invalidation, because tests mutate the DB in-process. | 1.5–2.5% |

### 2.3 V8's tiers: the hottest function never stays optimised

**Measured after 400 warm games** (`opt-status-run.log`). The status bits come from V8's
`OptimizationStatus` enum, and the raw value is printed beside each decode.

| Function | Final tier |
|---|---|
| `battleTurn` | **Baseline (Sparkplug) only**, raw value 32769 |
| `battleInit`, `dmgRange`, `battleOver`, `runPlayout` | Maglev |
| `playerAction`, `tags.param`, `tags.has`, `tags.tagsFor` | TurboFan |

**The same run's `--trace-opt` log:**

- `battleTurn` completed Maglev compilation **10 times** and aborted once ("dependency change"). It
  still ended the run at Baseline, which means the optimised code was repeatedly thrown away.
- `dmgRangeOneHit` also completed Maglev **10 times**.

**The `--trace-deopt` run (`deopt-run.log`):** every `battleTurn` bailout was **`deopt-eager`, reason
`wrong map`**, at bytecode offsets 95713, 96861, 112451 and 164518.

`wrong map` means an optimised site saw an object whose hidden class (its shape) it had not been
compiled for. The likely cause is that bodies, actions or field objects acquire properties in
differing orders, and many optional underscore fields are added lazily. **This is inferred and not
confirmed.** The sites are not yet mapped to source lines, and Batch 2 exists to do that.

`battleTurn` is also large enough that TurboFan's bytecode-size limit may refuse it outright. **That
is not measured either.** The log shows attempts at Maglev only, never at TurboFan.

### 2.4 Rollout versus narration

**The trace is already off in rollouts.** The header at `:4848` says so, and the code does it:

- `let TR=null`, and every emit site in the engine is `if(TR)TR.x(...)`.
- The trace is armed only by `battleInit(..., {trace: []})` (`:25869`).
- `rollout_leaf` never passes `trace`.

**What arming the trace costs:** rollout samples per turn go from **3.821** to **4.186, +9.54%**, and
the contended ms/turn ratio is **×1.091**. The functions that grow are `battleTurn`, `norm` (tag
lookups made by trace emits), and the trace emitters `mv` (`:4937`), `dmg` (`:5079`) and `push`
(`:4920`). **Only the differential and narration path pays this.**

**My own category over-matched, and is corrected here.** The first "trace emit" category matched
`traceSweep` and read 0.35% with the trace off. `traceSweep` (`:23602`) is the **Trace ability's**
re-attempt sweep (ROADMAP #310). It is a game mechanic, not narration. With the trace off, a rollout's
narration cost is the inline `if(TR)` tests plus the `MID_*` bookkeeping, and `midEventSlot` was
0.02%. Neither is measurable against the 0.28-point floor.

**The remaining non-board work a rollout does is instrumentation:**

- the tag counters `ASKED` and `COUNT`, about 1.2%;
- the `MEDSEEN` and `MEDFAILS` increments.

**These are how this repository proves a capability ran** (`tests/test-wiring.js`; the census reads
`ASKED`). **Do not skip them in a rollout mode. Make them cheaper**, with byte-identical counter
output.

- **`runPlayout`** (7.54% self) and the policy's own share. That code is in `rollout_leaf.js`, which

## 4. The correctness gate: defined precisely

**An optimization lands only if every clause below holds on a fixed release pair.** BEFORE is the
tree without the batch, and AFTER is the tree with it. Both are cut with `engine/engine_release.js`.
Every run pins three things, and records them:

- `--team-store data/team-pool-frozen`;
- a census copy passed to `--census`;
- the exact `--games`. **`--games` is part of the sample definition**, and its default is 45.

### Clause 0: the instruments are proven able to see a difference

- **Reproducibility.** Every instrument below is run **twice on BEFORE**. A field that differs between
  those two runs is excluded and listed, never silently ignored. Examples: timestamps, and the
  process-global stamps `_faintSeq` and `_rtieGen`, which are rank-normalised exactly as in
  `bench_clone.js`.
- **A red demo** for the self-differential. AFTER is run with a planted knob that changes behaviour,
  for example `MEDI_RESIDUAL_SORTS_BODIES=1` (`:9895`), and **the comparison must go red**. A plant
  that moves nothing on the game list is not a demonstration; pick another.

### Clause 1: the self-differential shows byte-identical boards and protocol

This is the verdict instrument. It replaces the "500-move × 4-turn whole-board digest sweep" named
in ROADMAP #130 and in `tests/bench-medicham.js`'s header, for which **no standalone file exists
today.**

The same pinned-pool game list is used for both releases: the same pairs, the same seeds, the same
body builder, `explore 1.0`, and the census switch rate. Each release runs in its **own process**,
and the run writes two things per game:

- **trace on:** every protocol line, plus a board digest at every turn boundary;
- **trace off:** a board digest at every turn boundary.

The pass condition is **byte-identical files, BEFORE against AFTER, in both modes.** It must also
reproduce this report's result that trace on and trace off give identical boards.

### Clause 2: the whole-game differential against Showdown reproduces

`engine/game_differential.js`, run with `--release BEFORE` and with `--release AFTER`, for each arm:
**`middle`**, **`top-tie-first`** and **`bottom-tie-first`** (from `const ARMS` at
`game_differential.js:1969`).

Use `--out` and `--dump-games N --dump-out` so that the published artifact is not clobbered. Compare
the two artifacts with stamps blanked, and **read the clauses, not the fields that look right**:

- `state.games`, `state.games_board_never_diverged`, and the full first-board and first-protocol
  divergence lists;
- `by_cause_totals`, the coverage block, and `undeclared_drops`;
- the full per-game dump, because the capped lists are not the population.

### Clause 3: the damage instruments reproduce at every roll index

- `tests/test-damage-stages.js`: every multiplier at every roll, exact. It stays **1728/1728**, with
  output byte-identical.
- `tests/test-engine-diff.js`: the top corner (roll index 0 against `max`) and the bottom corner
  (roll index 15 against `min`). Byte-identical output.

**Both read the live tree.** Run them at BEFORE, copy the output aside, apply the batch, then run
them again.

### Clause 4: the three roster stages reproduce

`tests/roster.js --stage item|ability|move --reds --write --release <R>`. It writes
`data/roster.<stage>.json`, so copy each result aside after every run. The per-stage artifacts must
be byte-identical with stamps blanked.

### Clause 5: the census reproduces

`node tests/test-mechanics.js` reads the live tree and regenerates `data/mechanics-census.json`. The
live count must be equal, and the census bytes must be identical with stamps blanked. **ENGINE's
number may not move in either direction** for an optimization.

### Clause 6: the twenty register probes reproduce

These are the 20 `VERIFIED BY:` instruments listed in
`docs/_reports/2026-09-11-owed-instruments.md`, runnable through `engine/register_reality.js`. Each
engine-loading probe is run with `--release BEFORE` and with `--release AFTER`.

The pass condition is **the same exit code AND the same stdout** with release ids blanked. Exit code
alone is too weak, because a probe that is red by design can stay red for a different reason.

### Batch-specific clauses

- **Batch 1:** the exhaustive memo self-check, and the `hits()`/`ASKED` snapshot comparison.
- **Batch 3:** both DB-mutating tests (`tests/probe_red_demo.js`, `tests/mutation_harness.js`), plus
  the planted post-index push.

### The stopwatch sits behind the gate

The stopwatch runs only after clauses 0–6 all pass.

- **One process loads both releases.** `tests/bench-medicham.js --vs` already loads a release beside
  the live tree in one process (`:150-151`). Before any timing, assert that the two releases'
  `data/engine-data.js` and `data/tags.json` digests are equal, because both instances share
  `globalThis.MC`.
- **It plays the same game list as clause 1**, trace off. Games alternate between the releases, with
  the order rotating.
- **It recomputes each timed game's digest in-process and asserts it equals clause 1's dumped
  digest.** That is what makes the speed figure and the equivalence **measured on the same games**,
  rather than on two samples that happen to share a name.
- **What it reports:** the median of per-rep paired AFTER/BEFORE ratios, the half-split noise floor
  of each arm, and absolute times labelled CONTENDED unless the machine was quiet.
- **The pass condition:** the ratio's improvement exceeds the noise floor.
- **What it may claim:** "×r on the pinned-pool rollout stopwatch, release pair X→Y". It may never
  claim a strength gain.
- `tests/bench-medicham.js --vs BEFORE` is a secondary reading only. It measures the two engines one
  after the other, not interleaved, so contention lands on one arm.

**The gate in one sentence.** On a BEFORE/AFTER release pair, every instrument is first shown
reproducible on BEFORE and the self-differential is shown red on a planted knob. Then the same
pinned-pool games must give byte-identical per-turn boards and protocol through both releases. The
three-arm game differential, damage stages, engine-diff corners, three roster stages, census and
twenty register probes must all reproduce their BEFORE output byte-for-byte with stamps blanked. Only
then does an interleaved in-process stopwatch, timing those same digest-verified games, report the
paired ratio.

## 6. What this does not claim

- **No speed-up is measured.** Every gain in §3 is an estimate from shares.
- **The absolute ms/turn figures are contended**, and they were taken with the profiler attached.
- **The unattributed declaration-line ticks** (`battleTurn` 4.79%, `runPlayout` 7.31%,
  `dmgRangeOneHit` 2.26%) are **explained only by hypothesis**.
- **TurboFan's size limit** on `battleTurn` is not measured.
- **The bodies here come from `buildMonFromSet`, not `freshBodies`**, so shares involving mega
