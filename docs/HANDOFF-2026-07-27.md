## 2. WHAT WAS FIXED: ENCORE, AND WHY THE FIRST FIX WAS NOT ENOUGH

The user, playing the bot, reported: *"this thing is encoring things that just switched in."* Encore
fails outright against a target with no last move. MAG could not see it — the whole
"this move cannot work right now" family (`deadStatus`, `deadSide`, `deadField`, `deadWeather`,
`deadStall`) was missing this member.

Added `GAME_RULES.needsTargetToHaveMoved = ['encore','disable','torment','spite','mimic','instruct','mirrormove']`
and feature #47 `deadNoLastMove`. Encore appears on **5.34%** of teams in this format (Disable 0.80%,
Instruct 0.31%), so it is not an edge case.

The fit agreed emphatically: **`deadNoLastMove` = −2.943**, 95% CI [−3.359, −2.528]. One of the
strongest negatives in the model. Humans essentially never click it.

**Then the user added: *"ESPECIALLY IF THEY HAVE PRANKSTER ENCORE"* — and that broke the first fix.**

The flag is not "the target has no last move." It is "the target has no last move **and I resolve
first**." A fresh switch-in has no last move *at the moment of the decision*, but it is about to make
one. If Encore is **slower**, the target moves, gains a last move, and Encore lands — that is the
normal, correct way the move is used. Only a **faster** Encore hits a target that still has not moved.

Which makes Prankster the worst case rather than a footnote: +1 priority on a status move means
Whimsicott, Sableye and Grimmsnarl essentially always resolve first, so Prankster Encore into a fresh
switch-in fails **every time**. The ungated version flagged the good play (slow Encore) exactly as
hard as the bad one.

The gate is `* x[FEATURE_INDEX.movesFirst]`, and it lives at the bottom of `featuresFor` with the
rest of the dead-move family, because move order is not settled until Tailwind, Trick Room and
priority have been applied further up. Verified:

```
Whimsicott (Prankster) -> fresh Garchomp        deadNoLastMove=1.00   movesFirst=1.00
Torkoal (slow, no Prankster) -> fresh Garchomp  deadNoLastMove=0.00   movesFirst=0.00
Whimsicott -> Garchomp that already moved       deadNoLastMove=0.00   movesFirst=1.00
```

Test script: `scratchpad/encore_test.js`. **Worth promoting into the repo as a real test** — this is
the second time a feature in this family was wrong in a way no automated check caught, and both times
a human playing the bot for ten minutes is what found it.

## 4. NEW FINDING: THE SET SAMPLER IS WRONG IN BOTH DIRECTIONS

The user, watching a battle: *"we should talk about the need for two stab moves, it's probably not a
realistic team construction choice for most pokemon. some will have two, but gunk and dire claw are
not it."* The bot had brought a Sneasler with **Dire Claw and Gunk Shot** — both Poison.

Measured against open team sheets (all four moves public, no revelation bias) from **2,245 clean
games**, 124 species. "Two or more *attacking* moves sharing a type":

| | humans | generated | gap |
|---|---|---|---|
| **all sets** | 28.5% | **34.7%** | +6.2 |
| Incineroar | **0.0%** | 22.5% | +22.5 |
| Raichu | 9.3% | 30.0% | +20.7 |
| Farigiraf | 0.0% | 14.5% | +14.5 |
| Garchomp | 26.7% | 37.0% | +10.3 |
| **Kingambit** | **98.9%** | **71.0%** | **−27.9** |
| Floette-Eternal | 100.0% | 83.0% | −17.0 |

**The user's instinct was right and the data is sharper than the rule.** Kingambit is the
counter-example that matters: Sucker Punch and Kowtow Cleave are both Dark and virtually every
Kingambit runs both, so a blanket "no two same-type attacks" rule would be wrong 99% of the time for
that species. The sampler over-produces doubles for Incineroar and *under*-produces the mandatory
ones for Kingambit.

**Cause** — `engine/champions_sim.js:142` → `set_priors.fillSet` draws each move **independently**
from P(move | species). Real sets are correlated *within a role*: Gunk Shot is a perfectly normal
Sneasler move (it appears on real sheets in the store) and so is Dire Claw, but they compete for one
slot, so marginal sampling pairs them at roughly P(a)·P(b). Independence cannot represent a slot.

**This matters more than it looks.** Only ~1.38 of 4 moves are revealed per set on the ladder, so
whatever fills the other 2.6 dominates any result built on generated teams — that is ADR-001's
lesson, and it has now recurred in a subtler form.

**Suggested fix, not yet built:** sample *whole observed sets* (or nearest-neighbour on the revealed
moves) instead of four independent marginals. Open sheets give 2,245 games × 12 complete sets of
ground truth to draw from, which is plenty. Audit script: `scratchpad/stab_audit.js` — promote it.
